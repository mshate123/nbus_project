# Requirements Document

## Introduction

This specification defines a clean, greenfield rewrite of the full-stack double-entry ledger and daily interest accrual system. The rewrite replaces the existing runtime architecture at cutover and does not import legacy database data. The contract preserves confirmed ledger invariants and useful read/write behavior while making API, proxy, authentication, deployment, accrual, UI, and browser verification deterministic.

**Spec location note:** `.kiro/specs/core-ledger/` is the intentional Kiro-native spec location for this request. The source reconnaissance and RCA package remains at `.specship/artifacts/reverse-engineering/`; no duplicate mission is created elsewhere.

## Scope

### In scope
- Python 3.12/FastAPI backend, async PostgreSQL persistence, migrations, domain/application boundaries, and executable accrual job.
- React/TypeScript ledger UI for accounts, statements, rate schedule, posting, and reversal.
- Docker Compose as the first and only supported deployment target for cutover.
- Stub bearer authentication on API routes.
- Seeded chart of accounts, demo journal data, and authoritative rate tiers.
- Contract, unit, property, integration, frontend, and containerized Playwright tests.
- Explicit test-layer ownership: backend tests under `backend/tests/`, frontend tests under `frontend/tests/`, and browser tests under the repository-level `e2e/` directory.
- Nginx API proxy preservation of `/api/*` paths.

### Out of scope
- Legacy data migration or import.
- S3, LocalStack, statement export, and object-storage workflows in the first cutover.
- Kubernetes, Minikube, CronJob manifests, and alternate deployment targets.
- Production identity, authorization roles, refresh tokens, or external identity providers.
- Multi-currency accounting, tax, budgeting, reconciliation, and report-builder features.

## Glossary

- **Ledger_API**: The FastAPI HTTP service exposing `/health`, `/ready`, and `/api/*` routes.
- **Ledger_UI**: The browser application served by nginx.
- **Posting_Service**: Application service that validates and atomically posts balanced entries.
- **Posted_Entry**: Immutable journal entry with status `POSTED` and one or more journal lines.
- **Normal_Balance**: Account direction, `DEBIT` or `CREDIT`, used to derive displayed balance.
- **Rate_Tier**: Exactly `standard`, `premium`, or `savings`.
- **Accrual_Run**: Idempotent operation that posts daily interest for eligible active accounts.
- **Error_Envelope**: JSON object with exactly `{ "error": "message" }` for application errors.
- **Proxy_Contract**: The rule that a browser request `/api/<path>` reaches the backend as `/api/<path>` unchanged.
- **Canonical_E2E**: the one-shot Playwright command executed by the dedicated `e2e-test` container with Chromium installed in its image.

## Requirements

### Requirement 1: Deterministic Compose startup
**User Story:** As an operator, I want a deterministic local deployment, so that the ledger can be started and tested without undocumented host dependencies.

#### Acceptance Criteria
1. WHEN the Compose app profile starts against an empty PostgreSQL volume, THE Ledger_API SHALL run migrations and expose `/health` with `{ "status": "ok" }` after the database is ready.
2. WHEN the API is accepting traffic, THE Ledger_API SHALL expose `/ready` with a successful status only after database connectivity and schema readiness are verified.
3. THE first-cutover Compose app profile SHALL run without S3, LocalStack, Kubernetes, Minikube, or required AWS environment variables.
4. THE production bootstrap seed SHALL be owned by migrations or an explicit seed command, and test fixtures SHALL be generated by a shared test factory module rather than treated as production seed truth.

### Requirement 2: API authentication and deterministic errors
**User Story:** As an API consumer, I want predictable authentication and errors, so that clients can distinguish authorization, validation, not-found, conflict, and server failures.

#### Acceptance Criteria
1. WHEN a request reaches an `/api/*` route without `Authorization: Bearer dev-token` or the configured stub token, THE Ledger_API SHALL return HTTP 401 with an Error_Envelope.
2. WHEN a request reaches an authenticated `/api/*` route with the configured stub token, THE Ledger_API SHALL process the request normally.
3. WHEN an API request contains a syntactically malformed UUID, THE Ledger_API SHALL return HTTP 422 with exactly one Error_Envelope and SHALL NOT execute a repository lookup.
4. WHEN an API request fails domain validation, references a missing account, or conflicts with an existing reversal, THE Ledger_API SHALL return HTTP 422, 404, or 409 respectively with one deterministic Error_Envelope.
5. WHEN an unexpected persistence or commit failure occurs, THE Ledger_API SHALL rollback the transaction, return HTTP 500 with one non-sensitive deterministic Error_Envelope, and leave no partial write.
6. THE Ledger_API SHALL return direct arrays for collection responses and direct objects for single-resource responses; successful responses SHALL NOT use `data` or `items` wrappers.

### Requirement 3: Account and rate data
**User Story:** As a ledger user, I want a seeded chart of accounts and authoritative rates, so that the application is useful immediately after cutover.

#### Acceptance Criteria
1. WHEN an authenticated client requests `/api/accounts`, THE Ledger_API SHALL return a plain JSON array ordered by `code`, with fields `id`, `code`, `name`, `type`, `normal_balance`, `rate_tier`, and `active`.
2. WHEN an authenticated client requests `/api/rate-schedule`, THE Ledger_API SHALL return a plain JSON array containing exactly `standard`, `premium`, and `savings` with annual rates `0.035000`, `0.045000`, and `0.050000`.
3. THE persistence model SHALL store `rate_tier` on each account and SHALL constrain every account to an authoritative Rate_Tier.
4. WHEN fresh database bootstrap completes, THE production seed SHALL contain a usable chart of accounts and deterministic demo entries sufficient for the Ledger_UI to show balances and statements.
5. WHEN an existing valid account has zero balance and no posted lines, THE Ledger_API SHALL return a successful zero balance and an empty statement rather than treating the account as missing.
6. WHEN an authenticated client references an inactive account for posting, THE Posting_Service SHALL reject the request with HTTP 422, deterministic error text, and no persisted rows.

### Requirement 4: Posting and ledger invariants
**User Story:** As an operator, I want to post balanced entries safely, so that every displayed balance is derived from auditable double-entry data.

#### Acceptance Criteria
1. WHEN an authenticated client submits `/api/journal-entries` with at least two valid one-sided lines whose Decimal debit total equals the Decimal credit total, THE Posting_Service SHALL create one Posted_Entry and return HTTP 201 with the direct entry object.
2. WHEN a posting request contains an unbalanced entry, a zero-value line, a line with both debit and credit, an amount with more than four decimal places, a missing account, or an inactive account, THE Posting_Service SHALL reject the request with HTTP 422 and SHALL persist no entry or line from the request.
3. WHEN a valid posting references multiple accounts, THE Posting_Service SHALL acquire account locks in deterministic UUID order and commit the entry atomically.
4. THE system SHALL derive account balances from posted journal lines using debit-minus-credit for DEBIT accounts and credit-minus-debit for CREDIT accounts; THE system SHALL NOT store a mutable balance column.
5. WHEN an authenticated client requests a statement, THE Ledger_API SHALL return posted lines in deterministic posting order with `entry_id`, `posted_at`, `debit`, `credit`, `running_balance`, and `reversal_of_id`.
6. WHEN a valid posting flushes but commit fails, THE Posting_Service SHALL rollback all entry and line rows and THE Ledger_API SHALL return HTTP 500 with the deterministic server Error_Envelope.

### Requirement 5: Reversal and auditability
**User Story:** As an operator, I want to reverse a posted entry without deleting history, so that corrections remain auditable.

#### Acceptance Criteria
1. WHEN an authenticated client posts `/api/journal-entries/{entry_id}/reverse` for a reversible Posted_Entry, THE Reversal_Service SHALL create exactly one new linked offsetting Posted_Entry and return HTTP 201.
2. WHEN an authenticated client reverses an entry that is missing, not posted, already reversed, or itself a reversal, THE Ledger_API SHALL return the documented 404 or 409 Error_Envelope and SHALL preserve all prior entries and lines.
3. THE system SHALL enforce at most one reversal per original entry with both application validation and a database uniqueness constraint.
4. WHEN a reversal conflict is shown in the Ledger_UI, THE Ledger_UI SHALL preserve the original posted row, display the deterministic conflict message, and avoid a false success state.

### Requirement 6: Accruals
**User Story:** As an operator, I want daily interest accruals to be repeatable and tier-aware, so that interest is correct without duplicate money movement.

#### Acceptance Criteria
1. WHEN an Accrual_Run processes an active eligible account for date `D`, THE system SHALL calculate interest as `balance * annual_rate / 365` using Decimal arithmetic and round half-up to four places.
2. WHEN an account has `rate_tier = T`, THE Accrual_Run SHALL use the annual rate for T rather than a global default tier.
3. WHEN an account/date pair already has an accrual, THE Accrual_Run SHALL produce no second accrual entry and SHALL report the existing result as idempotent.
4. WHEN an account has zero or negative derived balance, THE Accrual_Run SHALL produce no positive interest posting and SHALL record a deterministic skip reason.
5. THE repository SHALL provide an executable accrual command that accepts a date, commits successful work, returns a nonzero exit status on failure, and emits structured per-account results.

### Requirement 7: Proxy and browser verification
**User Story:** As a release engineer, I want browser tests to exercise the same API path users exercise, so that proxy regressions cannot masquerade as backend failures.

#### Acceptance Criteria
1. WHEN the Ledger_UI requests `/api/<path>`, THE Proxy_Contract SHALL forward the exact `/api/<path>` path to the Ledger_API without stripping the `/api` prefix.
2. WHEN the Canonical_E2E runs, THE dedicated `e2e-test` container SHALL provide Chromium from its image and SHALL execute browser flows without relying on a host browser cache.
3. THE Compose test profile SHALL expose separate one-shot services for backend tests, frontend tests, and Playwright E2E tests; the frontend unit-test service SHALL NOT be responsible for running Playwright.
4. THE Canonical_E2E preflight SHALL report direct backend status and frontend-proxy status separately, so a proxy routing failure is distinguishable from a backend failure.
5. WHEN seeded, empty, loading, or failed data is requested, THE Ledger_UI SHALL render accessible accounts, rates, and statements with explicit loading, empty, error-with-retry, happy, and responsive states.
6. WHEN an authenticated user completes post-then-reverse in the UI, THE Ledger_UI SHALL show the new entries, reversal label, and final derived balance without an API shape mismatch.
7. THE browser flows SHALL cover empty accounts/rates, API error, retry/recovery, posting validation failure, reversal conflict, loading, happy seeded data, and narrow responsive layouts as explicit state sequences.

## Non-functional requirements

- Money values SHALL use Decimal/NUMERIC(18,4); floating-point arithmetic is prohibited in domain calculations.
- API response and error shapes SHALL be versioned by contract tests and documented in `artifacts/api-contract.md`.
- Posted entries and lines SHALL be append-only at the application boundary; database constraints SHALL protect foreign keys, one-sided lines, tier values, and uniqueness rules.
- The UI SHALL use existing Tailwind/shadcn-style primitives and SHALL contain no inline styles.
- Backend unit, API, integration, and property suites SHALL run in the `api-test` container; frontend unit/component suites SHALL run in the `frontend-test` container; Canonical_E2E SHALL run only in the separate browser-equipped `e2e-test` container.
- The test directory contract SHALL be `backend/tests/` for backend tests, `frontend/tests/` for frontend tests, and repository-level `e2e/` for Playwright tests and browser fixtures.
- Backend engine coverage SHALL be at least 85%, backend API coverage at least 75%, backend overall coverage at least 70%, and frontend coverage at least 60%.
- The balance endpoint SHALL meet p95 latency below 200ms in the declared performance test.
- Health/readiness, structured job output, and API errors SHALL be diagnosable without exposing secrets.
- Concurrent posting SHALL preserve exact balances and SHALL not deadlock due to inconsistent account lock order.

## Resolved policy decisions

- Cutover: greenfield schema cutover with no data migration.
- Deployment: Docker Compose is the first deployment target.
- Storage/export: S3 and LocalStack are out of the first cutover.
- Auth: stub bearer authentication protects `/api/*`; token comes from configuration and defaults to `dev-token` in development.
- Missing accounts: balance and statement return 404; existing zero-balance accounts return 200 with zero/empty data.
- Inactive accounts: posting returns 422 and does not write.
- Rates: authoritative tiers are `standard`, `premium`, and `savings` with 3.5%, 4.5%, and 5.0%; accounts own `rate_tier`.
- Seed ownership: migrations or an explicit production seed command own bootstrap data; shared test factories own test data and tests assert equivalence rather than using test fixtures as production truth.
- E2E: the separate `e2e-test` Compose service runs Playwright in a container built from the browser-equipped frontend test image; frontend unit tests remain owned by `frontend-test`.
- Test ownership: backend tests live under `backend/tests/`, frontend tests under `frontend/tests/`, and browser tests under repository-level `e2e/`.
- Proxy: backend remains `/api/*`; nginx preserves `/api` exactly; direct and proxied preflight checks are separate.
